## What it is

b.green is for households that want to be more sustainable but lack one place to track it. One account holds the whole family, with up to a set number of profiles: an admin (usually a parent) and standard members. Members log appliance use and complete green tasks, such as turning off lights or recycling plastic, and earn points and XP. Points buy rewards the admin defines, such as picking the Saturday film. Levels, streaks, badges and a family leaderboard sit on top.

It was the team project for Web Programming I at ESMAD in 2025/26.

## The stores are the backend

With no server of our own, the Pinia stores carry the logic a backend would: validation, point accounting, level-ups, streaks, badge checks, and reward redemption and approval. Each action changes local state and then writes the household document back to json-server. The backup-and-rollback around each write came from a teammate's refactor; the logic inside the actions is mine.

The appliance emissions are the clearest example. The store calls the carbon API client. If that call throws, for example on a server error, the store falls back to a local estimate from the appliance's wattage and marks the result as local, so logging appliance use keeps working when the API is down.

There is a catch. The API client, mostly a teammate's, has its own local fallback for when no API key is configured, and that one does not label its result. So the same estimate is written twice, and a number can be local without saying so.

## The admin side

The admin dashboard is one page with collapsible, draggable sections for members, rewards, appliances, tasks and challenges. The admin adds and edits rewards there, and approves or cancels the ones members redeem. Cancelling refunds the points.

## What a backend would change

Most of the gaps above have the same fix: move the rules to a server.

- Real authentication: hashed passwords, sessions or tokens, and no credentials in URLs.
- Point and reward rules enforced on the server, inside transactions, so a balance can never go negative.
- Small endpoints per action (complete task, redeem reward) instead of rewriting the whole household.
- Check `response.ok` on every request and treat server errors as failures.
